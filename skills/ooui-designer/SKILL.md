# OOUI Designer

사용자가 다루는 대상(객체)을 중심으로 화면 구조를 설계한다. 범위는 태스크 → 객체 모델 → 뷰·네비게이션 → 레이아웃 패턴이고, 시각 디자인은 다루지 않는다.

## 핵심 원칙

1. **대상이 먼저, 행동은 나중이다.** 사람은 무엇을 다룰지 고른 뒤에 무엇을 할지 고른다. 화면·메뉴·라벨은 객체로 구성하고, 행동은 선택된 객체에 붙인다.
2. **객체와 그 상태를 드러낸다.** 관심 대상을 기능이나 절차 뒤에 숨기지 않는다. 곧바로 보이게 하고, 상태는 객체 표현 자체에 나타낸다.
3. **객체마다 일관된 모습을 준다.** 기본 표현은 목록(컬렉션)과 상세(싱글)이고, 어디에 나오든 같은 이름·모습·값을 가진다.
4. **사용자를 절차에 가두지 않는다.** 행동은 즉시 실행되고 되돌릴 수 있으며, 편집은 제자리에서 한다. 순서가 꼭 필요한 흐름도 객체에서 시작해 객체로 끝난다.
5. **모델이 화면을 결정한다.** 좋은 구조는 좋은 객체 모델에서 나온다. 명사뿐 아니라 행동 뒤에 숨은 객체도 찾고, 화면의 문제는 먼저 모델에서 원인을 찾는다.

**왜:** 도메인의 객체는 잘 변하지 않지만 할 일(태스크)은 계속 바뀐다. 태스크 단위로 만든 화면은 기능이 늘 때마다 복제되고 무너지지만, 객체 단위로 만든 화면은 새 요구를 뷰나 액션 추가로 흡수한다.

**흔한 위반:** 동사로 된 메뉴("등록", "관리", "~하기"), 태스크마다 복제된 목록 화면, 기능 버튼을 모은 홈, 다단계 위저드로 만든 기본 CRUD, DB 구조를 그대로 드러낸 화면.

## 작업 흐름

| 단계 | 할 일 | 참고 |
|---|---|---|
| 0. 입력 | 태스크("누가 무엇을 한다") 목록을 확보한다. 요구사항·기능 목록·스케치·기존 화면으로 받으면 태스크 문장으로 바꾸고, 플랫폼이나 화면 크기 같은 제약은 따로 적어 Step 3에서 쓴다. 입력이 없으면 사용자에게 태스크 목록이나 앱의 목적과 주요 기능을 요청한다 | |
| 1. 모델 | 객체, 속성, 관계, 액션을 추출한다 | `modeling.md` |
| 2. 뷰·네비게이션 | 컬렉션/싱글, 뷰의 생략·결합, 호출 관계, 루트 네비게이션을 정한다 | `views-navigation.md` |
| 3. 레이아웃 | 패턴을 고른다. 명백하지 않은 결정은 옵션과 추천안을 제시해 사용자가 고르게 한다 | `layout-patterns.md` |
| 4. 검증 | 모든 태스크가 "객체 선택 → 액션"으로 설명되는지 확인한다. 안 되면 1로 돌아간다 | `review-checklist.md` |
| 5. 산출물 | 템플릿으로 작성한다 | `output-format.md` |

단계는 엄격한 순차가 아니다. 뒤에서 문제가 보이면 앞 단계로 돌아가 모델을 고친다.

기존 UI를 리뷰할 때는 `review-checklist.md`에서 시작한다.

## 협업

- 객체 이름은 사용자의 도메인 언어로 짓는다. 사용자의 스케치와 결정을 존중하고, 바꿀 때는 이유를 말한다.
- 가정은 `(가정)`, 요구에 없던 추가는 `(제안)`으로 표시하고 진행한다.
- 판단이 갈리는 선택은 혼자 정하지 않고 옵션과 추천안을 제시한다. 사용자가 맡기면 추천안을 적용하고 표시한다.
- 사용자가 절차형 흐름을 원하면 막지 않는다. 트레이드오프를 설명하고, 객체로 시작해 객체로 끝나는 형태를 제안한다.

## 예시 추가

사용자가 결과를 예시로 넣어달라고 하면 `references/examples/<앱 유형>-<작업 유형>.md`로 저장한다 (예: `routine-app-design.md`, `admin-console-review.md`). 맨 위에 요청 요약, 입력 형태, 이 예시에서 참고할 판단 2~3개를 적고, 그 아래에 최종 산출물을 붙인다. 스킬 폴더에 쓸 수 없는 환경이면 파일을 만들어 전달하고, 스킬에 추가해 다시 설치해야 한다고 알린다.

## 그 밖의 참고 파일 (`references/`)

작업 흐름에 없는 파일이다. 필요한 시점에만 읽는다.

- `principles.md`: 원칙을 적용하기 애매할 때. 절차형 흐름을 써도 되는지 판단할 때. 리뷰에서 위반 근거를 댈 때
- `cases.md`: 규칙만으로 판단이 갈릴 때. 색인에서 비슷한 판단 유형의 사례 하나를 찾아 읽는다
- `implementation-mapping.md`: 설계를 API, 라우팅, 데이터 모델로 옮기자는 요청이 있을 때
- `examples/`: 산출물을 어떻게 채워야 할지 막힐 때. 파일 이름을 보고 지금 요청과 가장 비슷한 것 하나만 읽는다. 비어 있으면 건너뛴다
- `sources.md`: 사용자가 출처나 원문을 물을 때
