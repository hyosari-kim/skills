# Step 5. 산출물 형식

새 설계는 두 단계로 전달한다.

1. **중간 전달:** Step 1~2 결과 요약(객체 표, 뷰 목록)과 `layout-patterns.md`의 "레이아웃 선택 요청". 애매한 결정이 없으면 이 단계를 건너뛴다.
2. **최종 산출물:** 사용자가 고른 뒤 아래 템플릿 전체를 작성한다.

사용자가 한 번에 진행하라고 했거나 응답할 사람이 없으면 추천안을 적용해 바로 최종 산출물을 쓰고, 해당 결정을 `(가정: 추천안)`으로 표시한다.

최종 산출물은 항상 이 템플릿을 따른다. 리뷰 요청이면 `review-checklist.md` §3의 형식을 먼저 쓰고, 개선안을 이 템플릿으로 덧붙인다. 사용자가 일부만 요청하면 해당 섹션만 쓰되 번호와 제목은 유지한다.

```markdown
# [앱 이름] OOUI 설계

## 1. 요약
- 메인 객체: A, B, C
- 루트 네비게이션: [배치 패턴] — A / B / C
- 첫 화면: A [C] ([컬렉션 형식])
- 예외 흐름: [있으면 이름과 허용 조건 ID, 없으면 "없음"]

## 2. 태스크
| # | 태스크 | 비고 |
|---|---|---|

## 3. 객체 모델
### 3.1 객체 표
| 객체 | 역할 | 속성 (★ 핵심, ◆ 상태) | 관계 | 컬렉션 액션 | 싱글 액션 |
|---|---|---|---|---|---|

### 3.2 다이어그램
(Mermaid classDiagram)

### 3.3 판정 메모
- 객체로 채택하지 않은 명사와 이유 (예: "해결" → 안건의 상태 속성)

## 4. 뷰와 네비게이션
### 4.1 뷰 목록
| 뷰 | 종류 | 표시 속성 | 액션 | 진입 경로 | 생략·결합 ID |
|---|---|---|---|---|---|

### 4.2 생략·결합 결정
- [ID] [대상 뷰]: 근거 한 줄 (예: O3 태그 [S]: 속성이 이름뿐이라 제자리 편집으로 충분)

### 4.3 네비게이션 다이어그램
(Mermaid flowchart. [C]/[S] 표기, 결합은 subgraph, 점선 = 예외 흐름)

### 4.4 예외 흐름 (있을 때만)
- 허용 조건: T1/T2/T3 중 무엇이고 왜 해당하는지
- 입구: [객체] [S]의 "[액션]"
- 단계: 각 단계에서 생성·편집하는 객체
- 출구: [객체] [S]
- 흐름 밖 대체 경로

## 5. 레이아웃 결정
| 대상 | 결정 | 패턴 | 이유 | 결정 방식 |
|---|---|---|---|---|
(루트 네비게이션, 뷰 연결, 각 컬렉션 형식, 필터, 싱글 표시, 객체별 생성·수정·삭제. 결정 방식 = 명백 / 사용자 선택 / (가정: 추천안))

## 6. 태스크 커버리지
| 태스크 | 경로 (객체 → 액션) | 조작 수 |
|---|---|---|

## 7. 제안과 미결정 사항
- (제안) 요구사항에 없지만 추가한 것
- 결과를 크게 바꾸는 질문 1~2개
```

## 작성 규칙
- 객체 이름은 문서 전체에서 한 가지로 통일한다. 표, 다이어그램, 본문이 모두 같은 이름을 쓴다.
- Mermaid 식별자는 영문(`Agenda`, `AG_C`)으로 쓰고, 사람이 읽는 이름은 라벨(`["안건 [C]"]`)로 붙인다.
- 와이어프레임이 필요하면 뷰마다 ASCII 박스로 간단히 그린다. 시각 스타일은 넣지 않는다.
- 사용자가 구현 연결을 원하면 `implementation-mapping.md`의 표를 8번 섹션으로 덧붙인다.
