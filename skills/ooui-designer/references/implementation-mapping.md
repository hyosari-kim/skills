# 구현 매핑

먼저 프로젝트의 스택을 확인한다. 코드베이스가 있으면 설정 파일과 기존 라우팅·화면 구조를 보고, 없으면 사용자에게 묻는다. 아래 내용은 스택에 독립적인 개념 대응이고, 실제 코드는 확인한 스택의 관용구로 쓴다. REST가 아닌 스택(GraphQL, RPC, 서버 렌더링)에서도 원칙은 같다. 객체는 리소스나 타입, 컬렉션과 싱글은 목록 조회와 단건 조회, 액션은 변경 요청(뮤테이션)에 대응한다.

OOUI 모델은 API 리소스, 라우팅, 클라이언트 상태와 거의 1:1로 대응한다. 모델이 좋으면 API와 화면 구조가 같은 단위를 공유하므로 프론트엔드와 백엔드의 관계가 단순해진다.

## 1. 요소별 대응

| OOUI 요소 | API (REST 기준) | 클라이언트 라우트·화면 |
|---|---|---|
| 객체 | 리소스 | 객체 단위의 라우트 묶음 `/objects` |
| 루트 네비게이션 | — | 최상위 탭·사이드바의 각 항목 = 컬렉션 라우트 |
| 컬렉션 뷰 | `GET /objects` | 목록 화면 `/objects` |
| 싱글 뷰 | `GET /objects/:id` | 상세 화면 `/objects/:id` |
| 싱글톤 | `GET /account` | 단일 화면 `/account` |
| 자식 컬렉션 (N2) | 부모 단건 응답에 요약 N개 포함 + `GET /parents/:id/children` | 부모 상세 안의 섹션 + "모두 보기" 링크 |
| 필터·정렬 (V3) | 목록 조회의 쿼리 파라미터 | 같은 화면의 상태 (URL 쿼리) |
| 블랭크 생성 | 최소 속성으로 `POST /objects` | 목록에 낙관적 삽입 후 제자리 포커스 |
| 파라미터 생성 | `POST /objects` | 생성 폼 화면 또는 모달 `/objects/new` |
| 모드리스 에디트 | 필드 단위 `PATCH /objects/:id` | 디바운스 자동 저장 + 낙관적 갱신 |
| 삭제 + 되돌리기 | `DELETE` → 소프트 삭제, `POST /objects/:id/restore` | 목록에서 즉시 제거 + 되돌리기 알림 |
| 도메인 액션 | `POST /objects/:id/<action>` | 싱글의 액션 버튼 |
| 예외 흐름 | 흐름이 다루는 객체의 API를 그대로 사용 | 별도 라우트 묶음, 끝나면 싱글로 복귀 |

## 2. 응답 형태 규칙

- **컬렉션 응답**에는 핵심 속성(★)과 상태 속성(◆)만 담는다. 컬렉션 뷰에 보이는 것과 같다.
- **싱글 응답**에는 전체 속성과 관련 객체 요약(N2의 자식 N개, N4의 0..1 대상)을 담는다.
- 같은 객체는 어느 응답에 나오든 같은 형태(같은 필드 이름)를 쓴다. P5(같은 객체 = 같은 모습)의 API 버전이다.

## 3. 동기화 (P5)

- 클라이언트 캐시를 쓰는 스택이라면 캐시 키를 객체 단위(목록, 단건)로 둔다.
- 싱글에서 수정하면 해당 싱글 캐시를 갱신하고, 그 객체가 들어 있는 컬렉션 캐시도 갱신하거나 무효화한다.
- 같은 객체가 두 화면에 동시에 떠 있어도 같은 캐시를 읽으므로 자동으로 일치한다.

## 4. 대응 예

```
API                               화면
GET   /projects                   프로젝트 [C]  (루트 네비게이션)
GET   /projects/:id               프로젝트 [S]  (작업 [C] 요약 포함, C2)
GET   /projects/:id/tasks         작업 [C]
POST  /projects/:id/tasks         작업 블랭크 생성
PATCH /tasks/:id                  작업 모드리스 에디트
POST  /tasks/:id/complete         도메인 액션 (완료)
```

## 5. 주의

- 예외 흐름을 위해 전용 API를 만들지 않는다. 흐름은 객체들의 API를 순서대로 호출하는 UI일 뿐이다.
- DB에는 있지만 UI 모델에 없는 것(조인 테이블 등)은 API 응답에서도 숨긴다. API는 UI 모델의 모양을 따른다.
