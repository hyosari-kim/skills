## CASE-01. 기기 관리: 액션 이름 속의 객체
- 출처: 후지이 고타, 「OOUIデザインのトレーニング：アクションのオブジェクト化」 https://atochotto.com/654

**상황.** 기기 상세 화면에서 기기를 고른 뒤 "별칭 변경", "인증서 설정", "인증서 내보내기" 중 하나를 고르는 구조. 객체 → 액션 순서는 이미 지키고 있다. 인증서 목록은 "인증서 내보내기"를 눌러야만 보인다.

**적용 결과.**
- 액션을 "[기기]의 [X]를 [동사]"로 풀어 쓰자 별칭(속성)과 인증서(객체)가 드러났다.
- 기기 싱글 안에 인증서 컬렉션을 일체화했다. 추가, 설정, 내보내기는 인증서의 액션이 됐다.
- 기기와 인증서의 다중도는 따로 정리해야 한다.

**판단 포인트.**
- 객체 → 액션 순서를 지키고 있어도, 액션 이름 안에 명사가 있으면 꺼내본다.
- 특정 액션을 거쳐야만 보이는 객체는 "그냥 확인하고 싶은" 사용자를 막는다. 배운 사용자는 내보낼 생각이 없어도 매번 내보내기를 누르게 된다.
- 실제 메뉴 이름은 "권한 관리", "권한 인계"처럼 더 추상적일 수 있다. 실질적으로 무엇에 대한 조작인지 한 번 더 바꿔 읽는다.

## CASE-02. 신상 변경 신청: 행위를 객체로
- 출처: freee, 「2年目デザイナーが始めるOOUI」 https://developers.freee.co.jp/entry/start-userstory-ooui

**상황.** 직원이 결혼, 이사, 출생 같은 생활 이벤트를 신청하고 노무 담당자가 승인하는 기능. 유저 스토리에 "신청"과 "승인"이 비슷하게 자주 등장했다.

**적용 결과.**
- "신청"을 메인 객체로, 제출·승인·반려를 신청의 액션으로 정리했다.
- 모든 신청에 공통인 정보(신청일, 승인 경로)와 신청마다 다른 정보 묶음(주소, 전화번호, 부양가족)이 있었다. 신청은 정보 묶음들을 조합해 구성되는 것으로 모델링했고, 결혼 신청처럼 여러 묶음을 한 번에 내는 경우도 이 구조로 표현된다.
- 신청 화면은 공통 블록 다음에 신청별 블록을 나열하는 구성이 됐다.

**판단 포인트.**
- 유저 스토리에 자주 나오는 두 명사 중 하나가 다른 하나에 대해 하는 행위라면, 그것은 액션이다.
- 객체가 종류마다 다른 정보를 가지면, 공통 부분과 조합 가능한 정보 묶음으로 나눠 본다.
- 이렇게 만든 UI 모델은 데이터 모델과 거의 같아진다. 엔지니어와 함께 모델링하면 설계와 구현의 차이가 줄어든다.

## CASE-03. 게임 옷가게: 뒤엉킨 화면을 객체로 풀기
- 출처: 후지이 고타, 「OOUIデザインのトレーニング：ゲームの服屋」 https://atochotto.com/699

**상황.** 생활 시뮬레이션 게임의 옷가게. 매장에는 추천 상품 3개만 있고 전체 상품은 시착실에서만 볼 수 있다. 시착실은 신체 부위별로 하나만 고를 수 있는 배타적 선택을 체크박스로 보여주고, 시착 중인 조합만 함께 살 수 있다. 구매 후에는 바로 입을지 묻고, 입지 않은 옷은 자동으로 집으로 보낸다.

**처음 구조의 문제.** 상품을 보려고 시착실을 연다. 체크박스가 일반 다중 선택처럼 보인다. 같은 부위 옷을 여러 개 사려면 시착 → 구매 → 질문을 반복한다. 자동으로 집에 보내져 내가 무엇을 가졌는지 알기 어렵다.

**적용 결과.**
- 가장 중요한 객체를 상품으로 정했다. 매장 테이블을 고르면 전체 상품 컬렉션이 열려 상품 확인이 시착실에서 분리됐다.
- 구매 후 질문 흐름을 없애고, 산 것은 소지품에 들어가기만 하게 했다. 장착이나 보관은 필요할 때 사용자가 한다.
- 여러 개를 한 번에 사는 대신 연속 구매로 바꿨다. 구매 후 상품 목록에 머물고 결과는 모드리스 메시지로 알린다.
- 상품 하나의 시착은 "착용 이미지"라는 상품의 속성으로 바꿨다.
- 여러 상품의 조합은 "시착(코디네이트)" 객체로 정의하고 싱글만 뒀다. 객체로 만들자 여러 코디네이트라는 가능성도 보였다.
- 상품 컬렉션 옆에 시착 싱글을 두고 상품의 "시착" 액션으로 조합한다. 상품 싱글은 존재 의의가 약해져 생략했다. 시착 중 표시는 체크박스 대신 "시착 중" 라벨로 바꿨다.
- 다중 선택이 꼭 필요하면 선택 모드, 상시 선택, 장바구니 중에서 고른다. 둘러보려고 연 항목이 자동 선택되는 방식은 해제하는 수고를 만든다.
- 사기/팔기를 먼저 고르는 대신 상품과 소지품을 오가며, 상품에는 사기, 소지품에는 팔기 액션을 둔다.

**판단 포인트.**
- 여러 문제가 뒤엉켜 있으면 "가장 중요한 객체가 무엇인가"부터 정한다. 이상적인 구조가 보이면 문제는 그 차이로 드러난다.
- 선택을 강제하는 흐름은 질문을 늘릴수록 복잡해진다. 아무것도 하지 않는 기본 동작과 필요할 때 쓰는 객체 액션이 낫다.
- 복잡한 다중 선택을 설계하기 전에 연속 작업으로 충분한지 본다.
- 사용자가 머릿속에 함께 떠올리는 객체(상품을 고르며 떠올리는 소지품)는 같은 화면에서 다룰 수 있게 한다.

## CASE-04. 계약 관리: 동사 메뉴에서 객체 하나로
- 출처: 우에노 마나부, 「OOUI の目当て」 https://www.sociomedia.co.jp/8740

**상황.** 메뉴가 "신규 신청", "변경 신청", "해지 신청", "승인", "계약 조회"이고 각각 위저드의 입구라 전체 12화면이었다. 태스크마다 비슷한 검색과 목록이 반복됐다. "승인"은 권한자에게만 보였고, "계약 조회"는 내용만 확인하는 경우가 많아 따로 있었다.

**적용 결과.**
- 모든 메뉴가 "계약"에 대한 일이므로 계약을 메인 객체로 정하고 컬렉션과 싱글을 뒀다.
- 싱글을 참조용과 편집용으로 나눠 편집 의사로 전환하고, 편집용 싱글은 신규 생성 화면으로도 재사용한다.
- 컬렉션에 요승인 표시를 두고, 참조용 싱글에는 승인 권한자에게만 승인자 코멘트 칸을 보인다.
- 목록과 상세를 좌우로 나란히 둬서 차례로 확인하며 찾게 했다. 12화면이 한 페이지 앱이 됐다.

**판단 포인트.**
- 메뉴의 동사들이 모두 같은 명사를 대상으로 하면 그 명사가 메인 객체다.
- 보기가 대부분이고 편집은 드물거나 확정 절차를 거치면 참조용과 편집용 싱글로 나눈다.
- 권한에 따른 차이는 별도 화면이 아니라 같은 뷰의 조건부 표시로 처리한다.

## CASE-05. CMS: 하나뿐인 객체와 두 면을 가진 객체
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 웹사이트의 페이지를 추가, 편집, 정렬하는 앱. 상단 메뉴가 "페이지 추가와 삭제", "내용 편집", "페이지 설정", "사이트 설정"이었고, 추가·이동·삭제가 빈칸 채우기식 작은 위저드였다.

**적용 결과.**
- 화면의 명사에서 사이트와 페이지를 뽑았다. 둘 다 "설정"이 있고 페이지에는 "내용"도 있다.
- 사이트는 이 창에서 하나뿐이라 싱글만 두고, 페이지 컬렉션 위의 버튼으로 오른쪽 페인에 연다.
- 왼쪽에 페이지 컬렉션(추가, 삭제, 드래그로 순서 변경), 오른쪽에 페이지 싱글. 정보량이 많은 "설정"과 "내용"은 탭으로 전환한다.

**판단 포인트.**
- 하나뿐인 객체는 컬렉션 없이 싱글만 두고 다른 컬렉션 근처에서 연다.
- 성격이 다르고 둘 다 정보량이 많은 속성 묶음은 탭으로 나눈 싱글로 만든다.
- 순서 변경 같은 이동은 위저드가 아니라 드래그로 한다.

## CASE-06. 고객 관리·영업 지원 앱: 부모 싱글과 자식 컬렉션의 일체화
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 모바일 앱의 첫 메뉴에 "방문 예정"과 "방문 리스트", "안건 리스트"와 "안건 검색"처럼 명사와 동사가 섞여 있었다. "고객 정보"를 누르면 고객 목록이 아니라 "기업 검색", "고객 데이터 입력" 같은 할 일 메뉴가 나왔다.

**적용 결과.**
- 화면에 쓰인 명사에서 고객, 안건, 일정, 영업 자료를 뽑고, 고객은 다시 기업과 사람으로 나눴다(사람은 기업에 속한다).
- 메인 객체 네 개를 최상위 탭으로 두고, 고객 탭에서는 사람별·기업별로 찾는 방식을 전환할 수 있게 했다.
- 기업은 사람을 찾는 단서일 뿐이라, 기업 싱글을 그 기업의 사람 컬렉션과 일체화했다.
- 메시지 보내기는 사람 싱글의 액션이 됐다. 화면 수는 약 1/5로 줄 것으로 봤다.

**판단 포인트.**
- 명사와 동사가 섞인 메뉴는 모델링이 안 됐다는 신호다. 화면에 쓰인 명사를 주워 객체를 뽑는다.
- 부모가 자식을 찾는 단서 역할만 하면 부모 싱글을 자식 컬렉션과 합친다.
- 하나의 객체를 여러 단서로 찾게 하려면 별도 화면이 아니라 같은 탭 안의 뷰 전환으로 둔다.

## CASE-07. 숙소와 온천: 몇 개뿐인 자식 객체
- 출처: 니지박스, 「OOUI(オブジェクト指向UI)とは？」 https://blog.nijibox.jp/article/ooui/

**상황.** 온천이 있는 숙소를 찾는 여행 앱. 태스크에서 숙소, 온천, 천질(온천 성분 분류)을 객체로 뽑았다.

**적용 결과.**
- 숙소와 천질은 컬렉션과 싱글을 모두 뒀다.
- 온천은 숙소당 보통 1~3개라 싱글을 생략하고, 숙소에서 그 숙소의 온천 컬렉션을 불러 전부 보여준다.

**판단 포인트.**
- 부모당 인스턴스가 몇 개뿐이면 싱글을 생략하고 부모 쪽 컬렉션에서 모든 정보를 보여준다.
- 뷰가 늘면 화면도 는다. 필요 없는 뷰는 생략할 수 있다.

## CASE-08. 환율 계산: 입력 절차 뒤의 객체
- 출처: 우에노 마나부, 「OOUI の目当て」 https://www.sociomedia.co.jp/8740

**상황.** 금액과 통화를 입력하고 실행 버튼을 누르는 빈칸 채우기식 환율 계산기. 특정 태스크만 수행하도록 절차화되어 객체가 보이지 않았다.

**적용 결과.**
- 입출력 정보(원래 통화의 금액·종류, 대상 통화의 금액·종류)를 나열하고 공통 개념으로 묶었더니 "통화"라는 객체가 나왔다.
- 통화 뷰 두 개를 나란히 두고, 어느 쪽의 금액이나 종류를 바꾸면 다른 쪽이 환율에 맞춰 바뀌게 했다. 입력 순서와 실행 버튼이 사라졌다.

**판단 포인트.**
- 태스크형 입력 절차에서는 입출력 정보를 모두 적고, 공통 개념으로 묶고, 일반화한다.
- 실행 버튼은 대개 두 객체 사이의 동기화로 대체할 수 있다.

## CASE-09. 메일 클라이언트: 그릇 객체와 화면 크기
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 받은 메일을 다루는 앱에서 메일함과 받은 메일을 객체로 뽑았다. 메일함 하나에 메일 여러 개가 들어간다.

**적용 결과.**
- 메일함은 받은 메일 컬렉션을 불러오는 단서일 뿐이라, 싱글은 앞에 내지 않고 메일함 설정 화면 정도로 둔다.
- 넓은 화면에서는 메일함 컬렉션, 메일 컬렉션, 메일 싱글을 세 페인으로 나란히 두고, 좁은 화면에서는 같은 순서로 화면을 전환한다.

**판단 포인트.**
- 그릇 역할의 객체는 컬렉션만 있으면 충분하다.
- 모델은 그대로 두고 뷰의 배치만 바꿔 화면 크기에 대응한다. 페인 사이는 왼쪽에서 고른 결과가 오른쪽에 나타나는 방향을 지킨다.

## CASE-10. 비디오 카메라: 반복되는 목록과 국소 수선
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 메뉴가 "재생 기능", "편집·복사" 같은 할 일이었다. 방금 찍은 영상을 보려면 재생 기능 → 보기 방식 선택 → 이벤트 선택을 거쳐야 썸네일 목록이 나왔고, 삭제는 편집·복사 → 삭제 → 이미지 선택 → 동영상/정지화면 → 목록을 거쳤다. 두 경로의 목록 화면은 거의 같았다. 나중에 재생 화면에 휴지통 버튼을 붙이면서, 입구를 나눈 의미도 사라졌다.

**적용 결과.**
- 할 일 대신 "데이터 목록"으로 바로 녹화 데이터 목록을 보여준다. 기본은 단순한 시간순이고 다른 정렬·그룹은 옵션이다.
- 목록과 재생 화면에서 선택한 데이터에 삭제, 복사 액션을 둔다.

**판단 포인트.**
- 여러 태스크 경로에 거의 같은 목록 화면이 반복되면 그 목록의 항목이 객체다.
- 요구가 생길 때마다 흐름 중간에 기능을 덧붙이면 전체 모델이 무너진다. 국소 수선이 쌓였다면 모델부터 다시 본다.

## CASE-11. 사내 인트라넷: 추상적인 동사 라벨
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 글로벌 내비게이션이 "알다", "조사하다", "찾다", "익히다"였다. 수십 개의 이용 목적을 비슷한 것끼리 묶다 보니 라벨이 추상적인 동사가 됐다. 예를 들어 매뉴얼을 찾으려 할 때 네 개 중 어디에 있을지 예측할 수 없었다.

**적용 결과.** 그룹은 그대로 두고 라벨만 내용의 성격에 맞는 명사("공지", "사내 규정", "조직·직원", "연수")로 바꿨더니 크게 알기 쉬워졌다.

**판단 포인트.**
- 목적을 묶어 라벨을 붙이면 묶을수록 라벨이 추상적이 되어 내용을 예측할 수 없다.
- 콘텐츠를 찾는 시스템의 내비게이션 라벨은 콘텐츠의 성격을 나타내는 명사여야 한다.

## CASE-12. 이벤트 관리: 태스크를 컬렉션 형식으로 흡수
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 이벤트 등록, 일정 확인, 자재 수배를 그대로 흐름으로 만들어 비슷한 화면이 여러 개였고, 상세 검색 폼과 결과를 반복하는 DB 관리 도구 같은 형태였다. 자재 화면은 속성을 가로로 늘어놓은 표라 가로 스크롤이 생겼다. 원래 UI에는 여러 이벤트의 일정을 가로질러 보는 "일정 확인" 태스크가 있었다.

**적용 결과.**
- 이벤트와 자재를 객체로 뽑아 각각 컬렉션과 싱글을 뒀다.
- 이벤트 컬렉션을 처음부터 왼쪽 페인에 두고, 기본 형식을 간트 차트로 해서 이벤트를 가로질러 일정을 보고 마우스로 바로 바꿀 수 있게 했다. 간단한 필터 위에 필요할 때 상세 검색을 연다.
- 이벤트에 딸린 자재 컬렉션 오른쪽에 페인을 하나 더 두고 자재 싱글을 보여줘, 넓은 표를 대체했다.

**판단 포인트.**
- 여러 객체를 가로질러 보는 태스크는 별도 화면이 아니라 컬렉션 형식(캘린더, 간트 등)으로 흡수하고 직접 조작하게 한다.
- 가로로 넓은 표는 페인을 하나 더 두는 것으로 대체할 수 있다.

## CASE-13. 피자 주문 사이트와 식권 발매기: 선택보다 먼저 오는 확정
- 출처: 우에노 마나부, 「OOUI – オブジェクトベースのUIモデリング」 https://www.sociomedia.co.jp/7279

**상황.** 피자 주문 사이트의 첫 화면이 "메뉴", "주문하기", "매장 찾기"였다. "주문하기"로 들어가면 로그인, 배달지 지정, 확인 화면을 거친 뒤에야 피자를 고를 수 있었고, "메뉴"에서 시작하는 주문 흐름도 따로 있어 비슷한 위저드가 두 개였다. 같은 글의 식권 발매기는 메뉴를 보여주면서도 돈을 먼저 넣지 않으면 메뉴를 누를 수 없었다.

**적용 결과.** 첫 화면에 바로 상품 목록을 보여주고, 로그인과 장바구니는 헤더에 두어 언제든 쓸 수 있게 한다. 장바구니에 주문 버튼을 두고 거기서 배달지 지정 같은 주문 절차로 들어간다.

**판단 포인트.**
- 대상을 고르기 전에 로그인, 배달지, 결제 같은 확정 단계를 두지 않는다. 선택에는 위험이 없게 하고 의사 표시는 마지막 액션에 모은다.
- 같은 목적의 흐름이 두 개 있으면 혼란만 늘어난다.
- 예외적으로 ATM처럼 대상이 하나로 정해져 선택이 필요 없으면 절차형 흐름이 허용된다.
