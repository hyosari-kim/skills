# 원칙

SKILL.md의 핵심 원칙 5개를 세부 규칙으로 풀어 쓴 문서다.

| 핵심 원칙 | 세부 규칙 |
|---|---|
| 1. 대상이 먼저, 행동은 나중 | P1 |
| 2. 객체와 그 상태를 드러낸다 | P2, P3 |
| 3. 객체마다 일관된 모습 | P5, P6 |
| 4. 절차에 가두지 않는다 | P4, §3 절차형 흐름의 허용 조건 |
| 5. 모델이 화면을 결정한다 | P7, `modeling.md` |

## 1. 두 가지 조작 모델

| | 객체 지향 (Object-oriented) | 태스크 지향 (Task-oriented) |
|---|---|---|
| 조작 순서 | 객체 선택 → 액션 선택 (명사 → 동사) | 태스크 선택 → 대상·파라미터 지정 (동사 → 명사) |
| 네비게이션 라벨 | 명사 (객체 이름) | 동사 (할 일) |
| 사용자의 주의 | 일의 대상 자체 | 강요된 절차 |
| 모드 | 모드리스. 언제든 다른 객체로 옮겨갈 수 있다 | 모달. 절차를 끝내거나 취소해야 빠져나온다 |
| 적합한 곳 | 대부분의 정보 시스템, 특히 탐색이나 사용자의 궁리가 필요한 곳 | 대상 선택이 필요 없거나 정형 입력 절차만 제공하는 곳 |
| 확장될 때 | 뷰와 액션을 추가하면 된다 | 태스크마다 화면이 늘고 비슷한 목록이 복제된다 |

GUI는 원래 객체 지향으로 발명되었다. 화면에 보이는 대상을 가리켜 조작하는 것이 GUI의 기본 관용구이고, 명령어를 먼저 입력하는 CLI가 태스크 지향이다. 따라서 GUI에 태스크 지향 구조를 넣으면 GUI의 장점을 버리는 셈이 된다.

## 2. 규칙

각 규칙은 ID로 참조한다 (리뷰 결과에 "P4 위반"처럼 쓴다).

### P1. 명사 → 동사
- **적용:** 모든 액션은 대상이 정해진 상태(싱글 뷰, 또는 컬렉션에서 항목을 선택한 상태)에서 제시한다.
- **위반 신호:** "~하기" 버튼으로 시작해서 그다음에 대상을 고르게 하는 흐름. 대상을 고르기 전에 결제·로그인·옵션 같은 확정 단계를 거치게 하는 흐름.

### P2. 객체를 먼저, 가능한 한 빨리 보여준다
- **적용:** 앱 실행 직후와 루트 탭 진입 직후에 메인 객체의 컬렉션이 보여야 한다. 컬렉션이 비어 있으면 무엇이 여기에 쌓이는지 설명하고 추가 액션을 제공한다.
- **효과:** 사용자는 보이는 객체를 보고 앱의 용도와 범위를 파악한다. 컬렉션의 형식(캘린더, 그리드, 리스트)을 보면 조작 방식도 짐작한다.
- **위반 신호:** 첫 화면이 기능 메뉴다. 목적 대상이 보이지 않는 채로 여러 화면을 거쳐야 한다("터널").

### P3. 객체는 자기 상태를 스스로 드러낸다
- **적용:** 완료, 해결됨, 선택됨, 동기화 중, 오류 같은 상태는 객체 표현 자체(배지, 아이콘, 색, 형태, 위치)로 보여준다.
- **위반 신호:** 상태를 확인하려면 별도의 "현황" 화면으로 가야 한다.

### P4. 모드리스
- **적용:**
  - 액션을 고르면 추가 입력 없이 즉시 실행되고 결과가 즉시 보인다.
  - 속성은 그 자리에서 바꾼다. 별도 편집 화면이나 다이얼로그를 최소화한다.
  - 실수는 되돌리기(undo)로 수습한다. 되돌리기는 실패를 막는 장치가 아니라 **실패해도 괜찮게 만드는 장치**이고, 사용자가 시행착오로 배우게 해준다.
- **모드가 정당한 경우:** 여러 필드를 한 번에 확정해야 하는 경우, 편집 중인 상태가 다른 사람에게 보이면 안 되는 경우, 승인이 필요한 변경, 되돌릴 수 없는 파괴적 액션.
- **위반 신호:** 모든 편집이 "편집" 버튼 → 폼 → 저장 순서다. 모든 액션에 확인 다이얼로그가 뜬다.

### P5. 객체들은 서로 협조한다
- **적용:**
  - 같은 종류의 객체는 앱 전체에서 같은 모양과 같은 이름으로 나타난다.
  - 같은 객체가 두 뷰에 동시에 보이면 한쪽의 변경이 다른 쪽에 즉시 반영된다. 그래야 사용자가 둘을 같은 대상으로 인식한다.
  - 인접한 페인 사이에는 방향이 있다. 왼쪽이나 위에서 고른 결과가 오른쪽이나 아래에 나타난다.

### P6. 한 객체, 여러 뷰
- **적용:** 같은 객체가 캘린더, 리스트, 다른 객체의 싱글 안 요약 등 여러 곳에 나타날 수 있다. 뷰가 여러 개여도 객체는 하나이고 액션도 같다.

### P7. 절차보다 원리
- **적용:** 특정 맥락에 최적화된 절차는 다른 맥락의 사용자에게 불편하다. 여러 맥락에서 일관되게 통하는 원리(객체 + 액션)를 제공하고, 사용자가 자기 방식으로 목적에 도달하게 한다.
- **비유:** 사과 전용 껍질 깎기는 한 가지 용도에만 최적화되어 있지만, 과일칼은 사용법을 강요하지 않고 여러 상황에 쓰인다.

## 3. 태스크 지향이 허용되는 조건

다음 중 하나 이상에 해당하고, 근거를 산출물에 적을 수 있을 때만 태스크 흐름을 쓴다.

| ID | 조건 | 예 |
|---|---|---|
| T1 | 대상 객체가 하나로 고정되어 선택이 필요 없다 | ATM (카드를 넣는 순간 계좌라는 객체 선택이 끝난다) |
| T2 | 자기완결적인 정형 절차다 | 회원가입, 결제, 본인인증, 초기 설정 |
| T3 | 행동을 의도적으로 제한하는 것 자체가 목적이다 | 몰입형 루틴, 학습·튜토리얼, 안전상 순서 강제 |

**허용된 흐름에도 적용하는 규칙**
1. 흐름의 입구는 객체의 액션이다. 싱글이나 컬렉션에서 "시작" 같은 액션으로 들어간다.
2. 흐름의 각 단계는 가능한 한 객체를 생성하거나 편집하는 일로 표현한다.
3. 흐름이 끝나면 결과 객체의 싱글로 돌아온다.
4. 흐름이 유일한 경로가 되지 않게 한다. 같은 결과를 흐름 밖에서도 객체 액션으로 얻을 수 있어야 한다.

## 4. 태스크 지향 신호 (리뷰할 때 감지 규칙)

- 루트 네비게이션이나 메뉴에 동사가 있다: "등록", "조회", "관리", "~하기", "알아보기"
- 명사와 동사 라벨이 섞여 있다: "방문 예정" 옆에 "방문 검색"
- 거의 같은 목록 화면이 태스크별로 여러 개 있다
- 대상을 고르기 전에 액션을 고르게 한다
- 기본 CRUD가 다단계 위저드다
- 첫 화면이 기능 런처다
- 목적 대상이 보이지 않은 채 여러 화면을 거쳐야 한다
- 추상적인 동사로 묶은 그룹 라벨 때문에 무엇이 어디 있는지 예측할 수 없다
- 나중에 요구가 생길 때마다 기존 흐름 중간에 기능을 덧붙여 모델이 무너졌다 (국소 수선의 누적)
- 액션 이름 안에 명사가 들어 있다: "인증서 내보내기", "별칭 변경" (→ `modeling.md` AO1)
- 어떤 객체를 그냥 확인하려는데 출력·내보내기·리포트 같은 액션을 거쳐야만 볼 수 있다 (→ AO3)
- 결과를 보려면 "계산", "조회", "확인" 버튼을 눌러야 한다 (→ AO5)

## 5. 기대 효과

태스크 지향 구조를 객체 지향으로 바꾸면 화면 수가 대폭 줄고(참고 자료에 따르면 수 분의 1에서 수십 분의 1), 같은 목적에 필요한 조작 단계도 줄어든다. UI 모델, API, 데이터 모델이 같은 단위를 공유하게 되어 구현과 유지보수도 단순해진다.
