### Bug fix

**계획과 검증을 소유한다.**

과학적으로 한다. 배포되는 모든 줄은 런타임 증거로 추적된다. "도움이 될 수도 있는" 방어 코드는 수정이 아니라 가설이고, 싣지 않는다. 증거가 가설을 반박하면 그 가설이 만든 변경은 되돌린다. 증거가 정당화하는 가장 작은 수정만 낸다.

1. 사용자가 버그를 본 곳(화면, CLI, API 응답 등)과 같은 곳에서 직접 실행해 재현한다. 코드를 읽고 추론한 것은 재현이 아니다. 재현이 안 되면 조건을 좁히거나 계측해서 발생시킨다. 사용자에게 재현을 부탁하는 것은 내가 닿을 수 없는 구체적인 이유를 적을 수 있을 때만 한다.
2. 원인 후보를 세우고, 남은 범위를 가장 크게 가르는 분할부터 런타임 증거로 하나씩 배제한다. 상태가 불분명하면 로그를 넣고 실행하면서 읽는다. 추측하지 않는다. 회귀로 보이면 **hyosari-why**로 변경 이력을 본다.
3. 살아남은 원인(메커니즘)을 증거로 확인한 뒤에 수정을 계획한다. 함수나 모듈 경계를 넘으면 **hyosari-architect**를 쓴다.
4. 같은 방법으로 검증한다. 처음의 재현이 이제 통과해야 한다. "확인 불가"나 다른 환경에서의 확인은 통과가 아니다. 표시한다. 단위 테스트는 분기 동작을 보여줄 뿐 버그가 없다는 증거가 아니다.
5. 실패하는 재현(테스트)이 수정보다 먼저 히스토리에 오도록 커밋한다. 테스트를 쓸지와 쓰는 법은 **hyosari-tdd**를 따른다.
6. **Opening a PR**을 실행한다.

**Reply:** 무엇이 깨졌는지, 근본 원인, 수정, 검증 방법. 실패 → 통과 재현 출력을 그대로 붙인다.
