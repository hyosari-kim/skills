# 데이터 모델 이름 짓기

테이블 이름은 코드·쿼리·로그·ERD·대화에서 가장 오래 살아남는 이름이다. 뜻이 어긋난 이름은 그 위에 쌓이는 모든 코드가 오해를 물려받고, 운영 데이터가 생기면 바꾸기 비싸진다. 그래서 이름은 **처음 만들 때**, 그리고 **그 개념의 뜻이 바뀔 때** 점검한다.

## 언제 쓰나

- 새 테이블·모델·조인 테이블·다형 연관을 설계할 때 (이름을 정하기 **전에**)
- 설계 문서·하네스 step 문서가 새 엔티티 이름을 들고 올 때 — 문서의 이름은 "잠정"인 경우가 많고, 그대로 구현되면 굳는다
- 모델의 역할이 바뀌는 결정이 있을 때 (예: 한 곳에만 속하던 것이 여럿에 공유되게 됨)
- 사용자가 이름이 이상하다고 할 때 — 원인 분석과 대안을 함께 낸다

## 조건 (이유와 함께)

1. **한 행이 무엇인지로 짓는다.** "이 표의 한 줄은 ○○ 하나다"가 자연스러워야 한다. 역할에 대한 이미지(장부, 출처, 관리)로 짓지 말고 행의 실체로 짓는다. 이유: 쿼리를 읽는 사람은 행 단위로 생각한다.
2. **사용자·화면 용어와 1:1로 맞춘다.** 화면이 "보관처"라고 부르면 코드도 그 말을 옮긴 이름이어야 한다. 둘이 다르면 둘 중 하나가 틀렸다는 신호다. 이유: 기획·지원·개발이 같은 대상을 같은 이름으로 불러야 오해가 없다.
3. **이미 다른 뜻으로 굳은 단어를 피한다.** 업계·회계·영어 관용에서 정해진 뜻(book, source, journal, statement, account, ledger 등)은 그 뜻 그대로일 때만 쓴다. 이유: 읽는 사람은 사전적·업계 뜻으로 먼저 읽는다.
4. **관계가 문장으로 읽혀야 한다.** `transaction.fund_allocation.fund_location` → "거래는 어느 배분에 속하고, 배분은 어느 보관처에 있다". 소리 내어 읽어 어색하면 이름이 틀렸다.
5. **자기 데이터가 있는 연결 표는 개념 이름을 붙인다.** 두 표를 잇기만 하는 순수 조인은 `ledger_accounts` 처럼 두 이름을 붙여도 된다. 잔액·날짜·상태처럼 자기 데이터가 붙으면 그것은 독립 개념이므로 그 개념의 이름(`fund_allocations`)을 붙인다.
6. **같은 영역은 같은 접두로 묶는다.** `fund_*`, `budget_*`, `closing_*`. 이유: 테이블 목록만 봐도 영역과 소속이 보인다.
7. **구체적인 단어를 쓴다.** `data`, `info`, `item`, `record`, `detail`, `manager` 는 아무것도 알려 주지 않는다.
8. **줄임말을 쓰지 않고, 오해 없는 영어를 고른다.** 영어가 모국어가 아닌 팀은 단어의 첫 사전적 뜻으로 읽는다.
9. **한 단어는 한 뜻만.** 코드베이스에서 이미 다른 뜻으로 쓰는 단어를 새 개념에 재사용하지 않는다(예: `account` 가 계정과목이면 은행 계좌에 쓰지 않는다).
10. **프레임워크 관례를 따른다.** Rails 라면 모델 단수·테이블 복수, FK 는 `연관이름_id`. 예약어·기존 메서드와 겹치는 컬럼 이름(`changes`, `type`, `attributes`, `hash` 등)을 피한다.

## 진행 방법

1. **도메인 말을 모은다.** 사용자가 이 대상을 뭐라고 부르는지, 화면·문서에서 쓰는 한국어 용어를 먼저 확인한다. 코드베이스의 기존 테이블 이름과 문서(용어 정의, 아키텍처 문서)를 읽는다.
2. **한 행 문장을 쓴다.** 후보마다 "한 줄 = ○○ 하나" 를 한 문장으로 쓴다. 문장을 못 쓰면 모델 자체가 아직 흐릿한 것이므로 이름보다 모델을 먼저 정리한다.
3. **후보 2~3개를 비교한다.** 각 후보를 아래 빠른 점검으로 거른다.
4. **추천 하나를 이유와 함께 낸다.** 사용자의 도메인 언어를 우선하고, 판단이 갈리면 옵션으로 묻는다.
5. **바꾸는 경우 비용을 함께 말한다.** 운영 데이터가 있는지(배포 전이면 지금이 가장 싸다), 바뀔 것(테이블·FK 컬럼·인덱스·라우트·저장된 JSON 키·다형 타입 문자열)을 나열한다.

### 빠른 점검 (세 가지 중 하나라도 어색하면 다시 본다)

- 이름만 보고 주요 컬럼 3개를 맞힐 수 있는가?
- "X 는 Y 를 여러 개 가진다 / X 는 Y 에 속한다"를 소리 내어 읽으면 자연스러운가?
- 화면 용어로 번역했다가 다시 영어로 옮기면 같은 이름이 나오는가?

## 이미 있는 이름을 점검할 때 — 원인 찾기

이름이 뜻과 어긋났다면 아래 원인 중 무엇인지 짚어 준다. 같은 실수를 막는 데 도움이 된다.

- 설계 문서의 **잠정 이름**이 확정 없이 구현으로 흘러감
- 모델의 **역할이 바뀌었는데** 처음 이름이 남음
- **굳은 뜻의 단어**를 빌려 행의 실체와 다른 것을 말함
- **화면 용어와 코드 용어**가 따로 놂(맞춰 보는 장치 없음)
- 리뷰가 규칙·로직만 보고 **이름의 뜻은 보지 않음**

## 출력 형식

새 이름을 제안할 때:

```
## 이름 제안: <개념>
한 행: <이 표의 한 줄은 ○○ 하나다>
화면 용어: <사용자가 부르는 말>

| 후보 | 장점 | 걸리는 점 |
|---|---|---|
| ... | ... | ... |

추천: `<ModelName>` / `<table_name>` — <이유 한두 줄>
관계 문장: <소리 내어 읽은 문장>
```

기존 이름을 점검할 때는 이름마다 `맞음 / 바꿀 만함 / 꼭 바꿈` 과 근거(위 조건 번호), 바꾸는 비용을 적는다.

## 사례

| 처음 이름 | 문제 | 바꾼 이름 | 이유 |
|---|---|---|---|
| `CashBook` (`cash_books`) | "현금출납장"은 기록을 적는 장부인데, 한 행은 기록이 아니라 **기금 × 보관처의 몫**. 통장 몫도 담아 "cash"도 틀림. 화면 용어 "자금 배분"과 따로 놂 | `FundAllocation` (`fund_allocations`) | 조건 1·2·3·5. 시작 잔액·거래가 붙는 연결 표라 개념 이름 |
| `FundSource` (`fund_sources`) | 영어로 "자금의 출처(수입원)"로 읽히는데 실제 뜻은 **돈이 있는 곳**(통장·현금). 화면 용어 "보관처"와 어긋남 | `FundLocation` (`fund_locations`) | 조건 2·3 |
| `finance_changes.changes` (컬럼) | ActiveRecord 의 `changes` 메서드와 겹쳐 오류 | `field_changes` | 조건 10 |
| `Account` (계정과목) | 회계 관례(chart of accounts)에 맞아 유지. 다만 은행 계좌로도 읽히므로 계좌 뜻으로는 쓰지 않는다는 규칙을 문서·테스트로 고정 | 유지 | 조건 9 |

관계 문장 예: "회계는 기금을 여러 개 가진다. 자금 배분은 기금 하나와 보관처 하나의 몫이다. 거래는 자금 배분 하나에 속한다."
