# Hyosari why

**목표:** 설계 의도와 회귀 시점을 코드가 아니라 프로젝트의 기록으로 답한다.

**언제:** "왜 이렇게 만들었어?", "이 값은 왜 이거야?", "언제부터 이랬어?", 회귀로 보이는 버그. 지금 어떻게 동작하는지는 이 스킬이 아니라 코드를 따라 읽어서 답한다.

## 절차
1. 대상을 정한다. 파일과 줄, 심볼, 설정값, 동작.
2. 대상을 들인 변경을 찾는다.
   - `git log -S '<문자열>'` 또는 `git log -G '<정규식>'`: 그 코드가 처음 생기거나 바뀐 커밋.
   - `git blame -L <시작>,<끝> <파일>`: 지금 줄을 마지막으로 바꾼 커밋. 이동이나 포맷 커밋이면 `-w -C -C -C` 또는 `<커밋>^`부터 다시 본다.
   - `git log --follow -p -- <파일>`: 파일 이름이 바뀌어도 따라간다.
3. 그 커밋의 PR과 토론을 읽는다. `gh pr list --search <커밋 SHA> --state all`, `gh pr view <번호> --comments`. 연결된 이슈도 읽는다.
4. 이후 그 대상을 바꾼 변경도 같은 방법으로 읽는다.
5. 회귀를 찾는 중이면 정상이던 커밋과 깨진 커밋을 정하고, 실행 가능한 확인이 있으면 `git bisect run <명령>`으로 좁힌다.
6. 기록이 빈약하면 문서, ADR, 코드 주석, 관련 테스트 이름을 본다.

## 출력
- 결론 한두 줄.
- 근거: 커밋, PR, 이슈 링크. 정확한 표현이 중요한 곳은 짧게 인용한다.
- 내 추론은 "추론함"으로 표시한다. 작성자의 말과 섞지 않는다.
- 기록이 답하지 못하는 부분을 따로 적는다. 빈칸을 추측으로 채우지 않는다.

## 하지 않는다
- 코드만 읽고 의도를 단정하기.
- 추론을 작성자의 이유처럼 쓰기.
