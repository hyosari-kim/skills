# Explain the number

**목표:** 숫자를 보고하기 전에, 그 숫자가 주장하는 것을 실제로 쟀는지 확인한다.

**언제:** 성능 수치, 전후 비교, 회귀 주장, 라이브러리나 설정 선택처럼 숫자로 말하거나 결정할 때.
- 어림값이면 한 번 돌려도 된다. 대신 아래 4번과 7번은 확인하고 "1회 측정"이라고 적는다.
- 선택지 중 하나를 고르는 결정은 어림값으로 하지 않는다.
- 어림값은 사용자가 요청했을 때다. 나머지 점검은 그 1회 결과가 이상해 보일 때만 한다.

각 점검은 코드를 보고 짐작하지 않고 실행 결과로 답한다.

## 돌리기 전에
- 보고할 문장을 먼저 적는다. 예: "X로 p50이 120ms에서 80ms로 줄었다." 아래 점검은 그 문장을 시험한다.
- 스크립트를 읽어 무엇을 재고, 세고, 빼는지 본다.
- 기계 부하(`uptime`)와 코어 수를 본다. 부하를 멈출 수 없으면 A와 B를 번갈아 돌리고 그 사실을 적는다.
- 코어 수는 `nproc`로 본다. 기계가 바쁘면 무엇이 돌고 있는지 먼저 찾는다.

## 점검
1. **무엇이 한계인가.** 보고하지 않는 별도 실행에서 프로파일러로 병목을 찾고 소스 위치에 연결한다. 부하 생성기가 먼저 포화되지 않았는지 본다. 숫자가 안 움직였으면 쓸모없다고 하기 전에 병목부터 찾는다.
   - 프로파일러와 트레이서는 작업을 느리게 하므로 보고하는 실행과 분리한다.
   - 프로세스별 CPU(`top`, `pidstat`), 런타임 프로파일러(`node --cpu-prof`, `py-spy`, `perf`), I/O 대기, 시스템 콜 수(Linux에서 `strace -c`)를 보고 핫스팟을 소스에 연결한다.
   - 부하 생성기가 먼저 포화되면 잰 것은 부하 생성기다. 변경이 숫자를 못 움직였다면 그 이유는 병목이 설명한다.
2. **양쪽이 운영과 같은 조건인가.** 릴리스 빌드, 운영 플래그, 배치, 풀, 캐시 상태, 버전. 한쪽만 튜닝됐으면 구현이 아니라 설정을 비교한 것이다. 맞춘 뒤 다시 잰다.
   - 운영 환경 변수, 트랜잭션 설정, 연결 풀, 운영과 같은 정도로 데우거나 식힌 캐시, 같은 버전과 데이터까지 맞춘다.
   - 병목이 설정(행마다 커밋, 디버그 빌드, 빠진 인덱스)이면 그쪽은 튜닝이 안 된 것이다. 튜닝하고 다시 잰 뒤에 승자를 고른다. 튜닝할 수 없으면 그 실행으로 승자를 고르지 않는다.
   - 사용자가 무엇을 들일지 고르는 중이면 주장을 "지금 출하된 코드 기준"으로 좁혀도 해결되지 않는다. 사용자는 지금의 설정이 아니라 그 선택지를 들인다.
3. **한계를 넘지 않았나.** 대역폭, 작업 수 × 비용 대 코어 수를 본다. 전체의 X%인 부분을 없애도 속도 향상은 1/(1−X) 근처가 상한이다. 한계를 넘는 결과는 작업이 아닌 다른 것을 잰 것이다. 캐시, no-op, 버그가 흔한 예다.
   - 계산을 직접 한다. 초당 바이트는 디스크와 네트워크 대역폭과, 초당 작업 수 × 작업당 비용은 코어 수와, 줄어든 시간은 바뀐 부분이 원래 걸린 시간과 비교한다.
   - 예를 들어 전체의 10%를 차지하는 부분을 없애면 최대 약 11% 빨라진다.
4. **에러는 없나.** 실패와 성공이 아닌 응답을 세고, 출력이 맞는지 본다. 빠른 거절은 빨라 보인다. 스크립트에 에러 집계가 없으면 넣는다.
   - 거절은 대개 빠르고, 타임아웃과 재시도는 느리다.
5. **재현되나.** 양쪽을 최소 5번씩 번갈아 돌리고 중앙값과 범위를 적는다. 차이가 실행 간 편차 안이면 "측정 가능한 차이 없음"이다.
   - A, B, A, B 순서로 번갈아 돌려 워밍업, 지연 초기화, 캐시, 드리프트가 어느 쪽에도 유리하지 않게 한다.
   - 아슬아슬하면 순위합 검정(rank-sum test)이나 하네스 자체 통계를 쓴다.
6. **사용자에게 의미 있나.** 사용자가 기다리는 전체 경로를 실제 데이터 크기와 동시성으로 잰다. 부분 측정이면 전체 중 비율로 적는다.
   - 요청의 1%를 차지하는 헬퍼는 아무리 빨라져도 요청을 최대 1%만 빠르게 한다.
7. **일이 실제로 일어났나.** 잰 구간 안에서 요청이 서버에 닿았는지, 행이 쓰였는지, 바이트를 읽었는지, 결과가 쓰였는지 확인한다. 지연 실행과 타임아웃은 일어나지 않은 일의 숫자를 만든다.
   - 아무도 순회하지 않는 제너레이터, 아무도 await하지 않는 promise, JIT가 버릴 수 있는 결과가 흔한 지연 코드다.

## 보고
- 결론부터 쓴다. 빨라짐, 느려짐, 측정 가능한 차이 없음, 판단 불가.
- 숫자와 단위, 실행 횟수, 범위, 병목을 함께 적는다.
  예: "p50 41 ms → 33 ms, 쪽마다 7회 실행의 중앙값, 이후 범위 32~35 ms, 한 코어의 JSON 파싱이 병목."
- 차이를 주장하는데 병목을 못 찾았거나, 한쪽이 튜닝 안 됐거나, 4번이나 7번을 확인 못 했으면 "판단 불가"이고 빠진 것을 적는다.
- PR 본문에는 대표 숫자 하나만 쓴다. 나머지 실행 기록은 따로 둔다.
- 실행 기록, 범위, 병목 증거는 링크한 산출물이나 메모 파일에 둔다.

## 다른 성능 작업

- **Hillclimb** 플레이북(`hyosari-mode/playbooks/hillclimb.md`)의 하네스는 고정하기 전에 점검한다. 고정된 하네스는 에러 수와 작업 수를 출력하므로, 유지하거나 되돌리는 판단마다 4번과 7번이 저절로 확인된다.
