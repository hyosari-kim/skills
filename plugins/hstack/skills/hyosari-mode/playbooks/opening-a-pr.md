### Opening a PR

다른 모든 플레이북의 마지막 단계로 호출된다.

**먼저 확인한다.** git 저장소가 아니면 이 플레이북 전체를 건너뛴다. 원격이 없으면 로컬 커밋까지만 하고 push와 PR은 건너뛴다. 어느 쪽이든 할 일 목록에 사유를 한 줄 남긴다. push와 PR 생성은 SKILL.md의 Autonomy를 따른다. 세션 오버라이드가 없으면 push 직전에 브랜치 이름과 PR 제목을 보여주고 묻는다.

trunk에서 딴 별도 브랜치(가능하면 worktree)에서 작업하고, 관련 없는 변경은 섞지 않는다. 작고 병합 가능한 커밋으로 정리한다. 커밋 전에 diff를 한 번 훑어 디버그 흔적, 불필요한 주석, 이번 변경과 무관한 수정을 지운다. 커밋 전에 diff에 Claude Code `simplify` 스킬을 돌린다.

**제목:** `type(scope): subject`. 변경을 대표하는 실제 심볼이 있으면 이름을 넣는다.

**본문:** 리뷰어가 1분 안에 읽는 브리핑이다. 40줄 이내로 쓰고, 아래 `##` 제목을 이 순서로 쓴다. 빈 항목은 뺀다.

- `## Why` 목표와 이 변경이 필요한 이유.
- `## What changed` 무엇이 바뀌었는지.
- `## Scope` 하지 않은 것, 범위 밖으로 둔 것.
- `## Tradeoffs` 리뷰어가 물을 만한 기각된 대안만.
- `## Blast Radius` 이 변경이 영향을 줄 수 있는 곳.
- `## Verification` 실제로 실행한 검증과 그 결과.

PR을 열기 전에 Claude Code `code-review` 스킬(`medium`)을 돌리고, 확인된 버그는 고친 뒤 연다. 후속 PR은 앞선 PR의 브랜치를 base로 쌓는다. 프로젝트 관례가 draft가 아니라면 ready 상태로 연다. 프로젝트에 PR 템플릿이나 관례가 있으면 그쪽이 우선이다. PR을 열었다고 해서 상태 감시를 시작하는 것은 아니다. ready로 열 때는 `gh pr create`를 `--draft` 없이 쓴다. PR을 연 뒤에는 멈추고 PR 링크와 함께 보고한다.
