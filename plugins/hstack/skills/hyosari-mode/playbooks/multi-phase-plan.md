### Multi-phase or multi-PR plan

**코드가 아니라 계획을 소유한다. 계획은 담당자가 칸 하나씩 실행하고 운영자가 증거로 감사하는 체크리스트다.** 계획이 결과물이다. 구현하지 않는다.

1. 변경이 파일 한두 개이고 접근이 뻔하면 계획을 건너뛴다. 그렇다고 말하고 멈춘다.
2. 쓰기 전에 열린 질문은 `playbooks/prototype.md`에 따라 프로토타입으로 정한다. 운영자에게는 어떤 실행으로도 정할 수 없는 제품·취향 결정만 묻는다.
3. 계획 파일을 쓴다. 무엇이 바뀌는지, 들어갈 순서대로의 PR id, 의존 그래프로 시작한다. 의존 그래프는 어떤 PR이 독립적이라 trunk에서 따는지, 어떤 PR이 어떤 PR을 기다리는지, 각 PR이 건드려도 되는 파일을 말한다. 그다음 PR마다 섹션 하나를 둔다. PR 하나는 자기 증거를 가진 변경 하나다(**hyosari-principle-sequence-verifiable-units**). 각 섹션에는 의존하는 것, 수정하는 파일, 만드는 변경 하나, 보이는 결과, 검증에 대한 체크박스를 둔다.
4. 테스트만으로는 검증이 충분하지 않다. PR은 unit, live, perf 칸이 모두 체크되어야 검증된 것이다. 각 live 칸은 구체적인 시나리오와 통과 조건식으로 실제 화면을 돌린다. perf 칸은 지표, 측정 방법, 먼저 잰 trunk 기준값, 실패로 볼 숫자를 이름 붙인다. 인터랙션을 바꾸는 PR은 머지 전에 운영자의 리뷰를 기다린다.
5. 계획 경로를 돌려주고 멈춘다. 실행은 운영자가 명시적으로 시작하라고 할 때 시작한다.

**Reply:** 계획 경로, PR id와 그 의존 관계, 리뷰를 기다리는 묶음, 증명되지 않은 채 남는 것.
