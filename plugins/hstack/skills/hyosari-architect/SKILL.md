# Hyosari architect

**목표:** 코드를 먼저 쓰면 잘못된 모양이 굳는 작업에서, 구현 전에 모양을 정한다.

**언제:** 함수나 모듈 경계를 넘는 변경. 새 모듈, 새 공개 함수, 여러 파일에 걸친 데이터 흐름. 한 함수 안에서 끝나는 변경에는 쓰지 않는다.

**큰 설계:** 크거나 논쟁적인 설계는 혼자 스케치하지 않고 **hyosari-arena**를 쓴다.

## 절차
1. 변경이 닿는 곳을 모두 따라 읽는다. 호출처, 데이터가 들어오고 나가는 곳, 기존의 비슷한 구현.
2. 호출하는 쪽 코드를 먼저 적는다. 이 기능을 쓰는 사람이 실제로 쓰게 될 몇 줄이다.
3. 실제로 다른 모양 두 가지를 스케치한다. 각각 타입, 시그니처, 모듈 경계를 적는다. 이름만 다른 두 안은 두 가지가 아니다.
4. 아래 기준으로 하나를 고른다.
   - 상태마다 주인이 하나다.
   - 같은 일을 하는 방법이 하나다.
   - 호출하는 쪽이 내부를 가장 적게 알아도 된다.
5. 고른 안과 버린 안을 표로 남긴다. 되돌릴 수 없거나 사용자가 정해야 하는 갈림길만 묻는다.
6. 구현하는 동안 정한 모양에서 벗어나는지 본다. 우회 코드를 덧대야 한다면 땜질하지 말고 모양을 다시 정한다.

## 출력
- 호출하는 쪽 코드 예시.
- 고른 안: 타입, 시그니처, 모듈 경계.
- 대안 표: 안, 장점, 단점, 버린 이유.

## 하지 않는다
- 모양이 정해지기 전에 구현부터 쓰기.
- 간접층만 늘리고 분기나 불가능한 상태는 그대로인 설계.
