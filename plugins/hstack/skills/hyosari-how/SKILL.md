# Hyosari how

**목표:** 그 영역이 처음인 시니어 엔지니어가 바로 작업을 시작할 수 있는 정도의 머릿속 모델을 만든다.

**언제**
- 시스템, 하위 시스템, 코드 경로가 어떻게 동작하는지 물을 때.
- 코드를 바꾸기 전. 동작 모델 없이 고치면 처음 보이는 그럴듯한 곳에서 증상만 고치게 된다.
- 코드가 어디에 있어야 하는지, 어느 모듈이 소유하는지, 레이어가 맞는지 물을 때.

**쓰지 않는다:** 왜 그렇게 만들었는지 묻는 질문. **hyosari-why**로 간다.

## 절차
1. 범위가 모호하면 내 해석을 한 줄로 적고 진행한다. 사용자가 바로잡을 수 있게 한다.
2. 읽기 전용 서브에이전트 하나에 맡긴다. 파일 한두 개로 끝나는 질문이면 직접 읽는다.
   - 브리프 첫 줄은 hyosari-mode의 `worker.md`를 읽게 한다.
   - `subagent_type: "Explore"`로 띄운다. 브리프에 "파일을 고치지 않는다"를 쓰고, 끝나면 `git status`로 바뀐 파일이 없는지 본다.
   - 질문과 함께 이렇게 맡긴다. "그 영역이 처음인 시니어 엔지니어가 읽고 바로 작업을 시작할 수 있는 구조 설명을 써라. 주장마다 파일과 줄을 붙여라."
3. 실행하면 확인되는 동작은 실행해서 확인한다. 추측으로 메우지 않는다.
4. 서브에이전트 결과는 대화 맥락에 맞게 가볍게만 다듬는다. 크게 다시 쓰지 않는다.

## 출력
아래 순서로 쓴다. 작은 질문이면 해당 없는 항목은 뺀다.
- **개요:** 한두 문장.
- **핵심 개념:** 알아야 하는 타입, 상태, 용어.
- **동작 방식:** 진입점부터 실제 흐름. 파일과 줄을 붙인다.
- **어디에 있나:** 관련 파일과 모듈, 각자의 책임.
- **주의점:** 이름이나 겉모습과 다르게 동작하는 곳, 고칠 때 같이 봐야 하는 곳.

## 하지 않는다
- 설명 하나를 위해 서브에이전트를 여러 개 띄우기.
- 모호한 범위를 말없이 짐작하기.
- 동작 설명에 설계 의도를 섞기. 의도는 기록으로만 말한다.
